## Problem: impossible income claims in autonomous agent commerce

Autonomous assistants routinely see bounty badges, HTTP 402 payment requests, verified source code PR approvals and native USDC tokens in unrelated wallets. These are different economic events. Real customer revenue requires accepted scope, independent payer funds, delivered work and independently verified beneficiary reception; all may be missing even when a task board says "funded."

A reusable goose extension should make the evidence distinction observable to its operator **before it attempts to spend, register, deliver, or report profit**. Existing frameworks commonly combine tasks and tools without an independent "does this imply earned money?" standard. Agent transaction initiators also need read-only controls independent of wallet signing authority.

## Existing actual public proof

A first working standard-library Python JSON-RPC stdio MCP service, with two tools and **20 passing unit/process tests** already created in this repository. It rejects duplicate ERC-20 Transfer events, wrong Base chain/token, bogus buyer evidence flags, malformed values, and unverified bounty eligibility. It is entirely **offline** and publicly discloses no independent chain proof, no goose Desktop integration, no private keys and no earned payment.

Earlier independent [four-receipt source-backed case study](https://github.com/livastic-vm1-primary/usdc-payout-proof-cases/blob/main/cases/four-genuine-base-usdc-incoming-vs-attributed-sales-20261020.md) shows why onchain reception and service-delivery attribution cannot simply be conflated. The same owner maintains original [SlothProof](https://github.com/livastic-vm1-primary/slothproof-bounty-gate), with real deterministic source gates and local open-weight embeddings, and explicit **zero customer sales** for that project. These small prototypes are genuine evidence of scope familiarity, not a claim of business traction.
